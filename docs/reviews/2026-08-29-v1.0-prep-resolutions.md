## 1.1 PL leaves diverge at `lambda_l2 = 0` — **Fixed**

Commit `a90db89`. Two guards in `crates/backend_cpu/src/pl.rs`:

- **Ridge floor.** The effective ridge is now
  `max(lambda_l2, 1e-6 × mean diagonal of XᵀHX)`. An explicit `lambda_l2` is
  used verbatim (`max()`), so only the unregularized path changes. The
  pre-existing scale-disparity guard was reworked to keep measuring the
  *caller's* lambda — the floor is proportional to the mean diagonal, so
  letting it into that check would have silently weakened it (caught by an
  existing test that started passing when it should not have).
- **Leaf-output bound.** `XᵀHX` is accumulated in standardized coordinates, so
  its diagonal gives each regressor's in-leaf RMS and hence an `O(d)` bound on
  the leaf's output — no pass over the leaf's rows. A leaf whose bound exceeds
  `max_abs_leaf_value` is rejected and the split falls back to scalar leaves,
  rather than clamping at evaluation time (which would break the additivity the
  predictor and SHAP both depend on). `solve_pl_leaf` now returns
  `Option<LinearLeaf>`; `max_abs_leaf_value` reaches it via `LinearContext`.

Measured (California housing, 200 rounds, manual policy, `lambda_l2=0`):

| | before | after |
|---|---:|---:|
| train RMSE | 1,079,067 | 0.19 |
| test RMSE | 13.13 | 0.52 |
| `lambda_l2=10` test RMSE | 0.4456 | 0.4456 (unchanged) |
| top-k shortlist test RMSE | 1.53 | 0.62 |

**On the regression test.** The review asked for a λ=0 end-to-end regression
test. That turned out not to be constructible: the original blow-up is a
numerical knife-edge tied to one specific split on one specific train/test
partition — reshuffling the *same* dataset avoids it, and none of the synthetic
fixtures tried (collinear pairs at four tightness levels, heavy-tailed and
lognormal columns, rank-deficient leaves, a California-shaped 8-column
generator) reproduce it. The guards are therefore pinned by four deterministic
unit tests in `pl.rs` (`ridge_floor_applies_only_when_below_caller_lambda`,
`unregularized_collinear_system_is_bounded_by_the_ridge_floor`,
`leaf_output_guard_rejects_unbounded_linear_term`,
`solve_pl_leaf_returns_none_when_output_exceeds_ceiling`). The Python tests
added alongside are labelled as end-to-end *invariants* rather than as
reproductions, because they pass with the guards disabled and claiming
otherwise would be misleading.

## 1.2 SHAP brute-force path — **Fixed**

Commit `720e16d`. `MAX_EXACT_SPLIT_FEATURES = 25` routed any model splitting on
≤ 25 distinct features — most real tabular models — to the legacy exponential
Shapley path. TreeSHAP is exact for tree models, so every production call now
uses it; brute force is retained behind `#[cfg(test)]` as a parity oracle.
Rows are additionally explained in parallel with Rayon (they are independent
given the shared `std_trees`; the indexed collect preserves order).

Measured on a 50-tree depth-6 12-feature model, 200 rows: **18.2 s → 0.015 s**
(91 ms/row → 0.07 ms/row).

## 1.3 Inert exclusive feature bundling — **Partially fixed (deliberately)**

Commit `8701284`. Confirmed the diagnosis: on 40 exclusive one-hot columns,
linear binning bundles all 40 while quantile (the default) bundles none,
because discovery treats bin 0 as a feature's empty value and quantile binning
does not guarantee a raw `0.0` lands there.

**What shipped:** a `UserWarning` naming the likely cause whenever bundling was
requested but produced no bundles, plus docs stating the bin-0 requirement.
Silent no-ops are now impossible.

**What did not ship, and why.** The review recommended generalizing discovery to
each feature's modal bin. Investigating first revealed a more fundamental
problem: **bundling is not currently a speedup at all.** The bundled histogram
kernel reads the storage column once but still performs one accumulator update
per *original* feature per row — the same work as not bundling. A prototype
bundle-level kernel (accumulate once per bundle, then scatter each member's
bins in `O(span)`) was written and measured: **1.22× in row-dominated regimes**
(1M rows × 60 columns) but **0.69× when feature-count-driven materialization
dominates** (120k rows × 205 columns), because per-original-feature histograms
are still materialized and scanned downstream.

It also **broke a deliberate invariant**: bundled and unbundled fits currently
produce byte-identical artifacts, and bundle-level accumulation changes float
summation order. That guarantee makes turning bundling on provably safe. Trading
it for an inconsistent speedup immediately before v1.0 was the wrong call, so
the prototype was reverted and the finding recorded instead. Realising EFB's
usual win requires a **bundle-aware split scanner** — an architectural change
that also forfeits byte-equality, and belongs in a release with room to
validate it.

## 2.1 `n_estimators` default — **Fixed**

Commit `4409499`. Default `6 → 100` across all estimators and the joint bridge.
Fixing this surfaced two genuine classifier-probability bugs in the same area,
also fixed: `predict_proba` rounded to 7 decimals (manufacturing exact-zero
probabilities without renormalizing), and `predict_log_proba` clipped
inconsistently with it. The sklearn conformance harness now mirrors sklearn's
own `HistGradientBoosting*` policy of expecting
`check_sample_weight_equivalence_*` to fail, since histogram bin cuts derive
from unweighted quantiles.

## 2.2 Ranking truncation default — **Fixed, with a caveat the review missed**

Commit `5be6650`. `lambdarank_truncation_level` defaults to `30`, matching
LightGBM, shared between `GBMRanker` and the joint bridge.

Measured on 50 groups of 2,000 documents (50 rounds):

| configuration | fit | NDCG |
|---|---:|---:|
| all pairs (previous default) | 3.65 s | 0.9901 |
| truncation 30 (new default) | 2.05 s | 0.9735 |
| LightGBM (its own default) | 0.47 s | 0.9727 |

The review presented this as a straightforward speed win. It is not: truncation
**costs ranking quality** (0.9901 → 0.9735 here), which the review had not
measured. The default still changed — it matches the industry standard, bounds
a pathological `O(n²)`, and beats LightGBM's NDCG at comparable settings — but
the docs now carry both sides of the trade and a group-size rule of thumb,
rather than presenting it as free.

## 2.3 `dart_skip_drop` — **Fixed, and it closed the gap**

Commit `31e9e2a`. Added `dart_skip_drop` (default `0.5`, LightGBM's
`skip_drop`), rolled once per round with its own mixing constant so the skip
decision is independent of the per-tree dropout draws.

| configuration | fit | test RMSE |
|---|---:|---:|
| `skip_drop=0.00` (previous behaviour) | 1.21 s | 0.6241 |
| `skip_drop=0.50` (new default) | 0.77 s | **0.4815** |
| LightGBM DART (its own default) | 1.18 s | 0.5238 |

The new default is ~1.6× faster than the old behaviour *and* more accurate than
LightGBM's DART, which more than closes the 19 % gap the review flagged.
`dart_skip_drop=0.0` reproduces the previous behaviour exactly.

## 2.4 Training throughput at scale — **Investigated; root cause identified, not fixed**

Commit `574f5ef` adds the visibility the review asked for: the perf gate gained
a 50k-row × 40-feature quick scenario (125k × 50 for full runs), so the
`fit(2N)/fit(N)` scaling check now exercises the regime where histogram
construction dominates rather than per-round fixed costs. Cost: ~2 s of CI.

Profiling identified the actual cause of the gap, which the review had left
open: **parallel scaling is poor**, not single-thread speed. On a 10-core
machine at 250k × 50, `n_jobs=1` takes 4.64 s and unlimited threads take
2.40 s — a 1.9× speedup on 10 cores, against LightGBM's 1.44 s. The
single-threaded work is competitive; the thread utilisation is not. Fixing that
is the architectural item (interleaved gradient/hessian layout, in-place row
partitioning, deeper node-level parallelism) and is left for a 1.0.x with room
to validate.

## 2.5 Polish — **Fixed**

- **`training_mode="auto"`** (commit `574f5ef`): documented as delegating the
  split-criterion choice to AlloyGBM, currently resolving to the standard
  criterion — behaviourally identical to `"manual"` today — with the
  distinction that `"auto"` may become adaptive while `"manual"` is a
  commitment across upgrades. Callers who need stability are told to pin
  `"manual"`.
- **CI mode-quality pins** (commit `1f3abe1`): new
  `benchmarks/mode_quality_gate.py` trains 21 mode configurations on fixed
  seeds and asserts two machine-independent invariants per mode — beats the
  constant predictor, and stays within a factor of the plain-boosting baseline
  from the same run. Both are within-run ratios, so they hold across CI
  runners where absolute RMSE thresholds would not. Contract tests exercise the
  gate's own invariants against the historical failure shapes. Replaying
  history: the GOSS and DART regressions trip it comfortably; the PL blow-up
  does not reproduce synthetically (see 1.1), and the docstring says so rather
  than implying coverage it lacks.
- **Release mechanics**: `CHANGELOG.md` now records every breaking default
  change with its measured before/after.

## Additional findings from this pass

Not in the original review; found while verifying the fixes.

- **`GBMClassifier.predict_proba` rounding** — fixed in `4409499`, see 2.1.
- **GIL-release tests became contention-sensitive** (commit `9dcd8b9`). These
  compare a Python worker thread's progress during a native call against a
  sleep. Parallelising SHAP means the Rayon pool now saturates every core, so
  the worker competes for CPU even though the GIL is genuinely free — one run
  failed exactly this way under load. The ratio was relaxed from 0.25 to 0.05
  and named, with a comment recording that a held GIL drives worker progress to
  ~zero, so the bound still separates the two regimes without doubling as a
  scheduling-fairness assertion. This is a regression risk introduced by the
  SHAP change, caught only because the failure was investigated rather than
  retried.

## Verified sound (no action needed)

Checked during this pass and found correct:

- **Edge cases and error messages**: constant target, single row, single
  feature, all-NaN column, empty predict, `inf` in `X`, NaN in `y`,
  `n_estimators=0`, negative learning rate, single-class classifier, predict
  before fit, feature-count mismatch — all produce clear, actionable errors.
- **Persistence**: pickle and `save_model`/`load_model` round-trip exactly for
  regressor, PL leaves, DART, binary classifier, multiclass, ranker, and joint
  multi-output.
- **Determinism**: byte-identical artifacts across repeated fits for standard,
  subsample, GOSS, DART, MorphBoost, PL, leaf-wise, and `colsample_bynode` —
  and **identical across `n_jobs=1` vs `n_jobs=4`**, which is a strong property
  to be able to claim at v1.0.
- **API consistency**: all estimators return `ndarray` from `predict` with the
  expected shapes, and expose the same fitted-attribute surface.

## Remaining for after v1.0

1. **Parallel scaling** (2.4) — 1.9× on 10 cores is the headline performance
   opportunity.
2. **Bundle-aware split scanner** (1.3) — required for EFB to be a real
   speedup; forfeits artifact byte-equality, so it needs its own validation
   cycle.
3. **Modal-bin bundle discovery** (1.3) — makes EFB reachable under the default
   binning; worth doing *after* (2), since it is only valuable once bundling
   actually pays.
