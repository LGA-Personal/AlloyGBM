# AlloyGBM competitiveness review: accuracy diagnosis and CPU priorities

| Date | Reviewer | Version reviewed | Commit | Status |
|---|---|---|---|---|
| 2026-09-06 | Codex, with focused LightGBM/XGBoost/CatBoost source reviews | 1.0.0 | `126a0694b5c02dcba8d454a45e65eb3beb4739f3` | Open — diagnostic evidence collected; production changes not implemented |

**The strongest finding is a quantile-bin budgeting defect, not evidence that AlloyGBM needs a different boosting algorithm.** On the original 500k×40, 200-round, depth-8 fixture, correcting the quantile grid in an external preprocessing probe reduces RMSE from **0.163775 to 0.152451**, essentially eliminating the observed gap to LightGBM (**0.152700**). Changing only the existing binning option to `linear` improves RMSE further, to **0.134126**, and beats the existing peer configurations on three seeds of this generator. Disabling the automatic gain floor produces identical predictions and tree artifact bytes on the original fixture.

Single-thread speed remains a separate, real problem. The first implementation experiments should remove redundant missing-direction scans, specialize constant-Hessian accumulation, and avoid unnecessary child-histogram and buffer work. None requires unsafe Rust or weakening cross-`n_jobs` determinism.

## Evidence and scope

Reviewed the scalar training loop, level/leaf builders, histogram storage/accumulation/scanning, binning bridge, policy resolution, categorical encoding, benchmark factories/gates, and previous review resolutions. This is a targeted competitiveness review, not an exhaustive correctness audit of every objective or platform.

The existing `.venv` imported AlloyGBM from the clean `competitiveness-benchmark-gates` worktree at `288c170`. Its library source matches the reviewed checkout; only the changelog differs. Nevertheless, all new fits used a freshly built release wheel from the reviewed checkout, installed into an isolated temporary directory. The shared environment was not reinstalled. Build/package hashes, versions, commands and limitations are in [provenance.json](data/2026-09-06-competitiveness/provenance.json).

The diagnostics reuse `benchmarks/deep_scaling_comparison.py`'s dataset and factories and `benchmarks/auto_policy_benchmark.py`'s policy-arm derivation. They do not replace the competitiveness gate harness. [Raw results and executed drivers](data/2026-09-06-competitiveness/README.md) accompany this review. Fits ran sequentially with profiling off; these single-fit timings are descriptive, **not performance acceptance evidence**. No full Rust/Python suite was run because no library implementation changed.

## Accuracy: controlled results

All raw-feature fits below use 500,000 rows × 40 features, the original 80/20 split, 200 rounds, depth 8, learning rate 0.05, row/column sampling 0.8, and one thread. The generator is Gaussian features, a five-feature linear signal, one interaction, and noise standard deviation 0.1.

| Original seed `20260902` | Test RMSE | Train RMSE | Fit seconds |
|---|---:|---:|---:|
| Alloy current auto / quantile 256 | 0.163775 | 0.145971 | 16.392 |
| Same, remove gain floor only | 0.163775 | 0.145971 | 16.484 |
| Manual defaults, leaf minimum 1 | 0.164085 | 0.142773 | 17.044 |
| Same auto policy, linear 256 | **0.134126** | 0.124169 | 15.870 |
| Same auto policy, quantile 1024 | 0.138222 | 0.123912 | 28.242 |
| Repeat original baseline | 0.163775 | 0.145971 | 16.804 |

The resolved auto policy is 200 completed rounds, minimum leaf size 16, minimum gain approximately `1e-4`, L2 zero, and the requested sampling rates. The small/noisy-data auto-L2 rule is inactive by construction above 1,024 rows ([policy.rs](../../crates/engine/src/trainer/policy.rs)). There is no early-stop or reduced-round confound here. Removing the gain floor gives the same artifact SHA-256 as baseline; reducing minimum leaf size fits training data better but generalizes slightly worse. This rejects the proposed auto-over-regularization explanation for this fixture, not for every workload.

The independent-seed confirmation reran all four libraries contemporaneously:

| Seed | Alloy quantile 256 | Alloy linear 256 | LightGBM | XGBoost | CatBoost |
|---|---:|---:|---:|---:|---:|
| 20260902 | 0.163775 | **0.134126** | 0.152700 | 0.154052 | 0.145909 |
| 20260903 | 0.165675 | **0.137165** | 0.155533 | 0.155468 | 0.148700 |
| 20260904 | 0.166358 | **0.136219** | 0.157063 | 0.156206 | 0.148365 |

The extra seeds confirm the same distribution, not broad superiority. Linear binning was selected after inspecting the first seed, and competitors have not received equivalent tuning. These are sensitivity results, not a new leaderboard.

The tail diagnosis is particularly informative: on the original test set, 3.885% of rows have `abs(x)>2.65` in at least one signal feature. Their RMSE falls from **0.475522 to 0.207421** with linear binning; central-row RMSE falls from **0.136991 to 0.130300**. That small tail subset accounts for about 32.8% of baseline squared error. Quantile bins discard useful resolution in these continuous tails, which additional trees cannot recover from constant leaves.

### 1. Correct the quantile data-bin budget — highest priority

**Where:** `quantile_cuts_from_sorted_values` and `quantile_cuts_from_weighted_values`, called by `derive_dense_feature_quantile_cuts` / `prepare_training_matrices_from_dense_values` in [quantization.rs](../../bindings/python/src/quantization.rs); matching Python helper `_single_feature_quantile_cuts_from_sorted_values` in [_quantization.py](../../bindings/python/alloygbm/_regressor/_quantization.py).

**Mechanism:** with `max_bins=256`, cut generation produces 255 cuts for 256 quantiles. Quantization then clamps the insertion index to `max_bins-2=254`, reserving a missing bin. The final cut cannot distinguish two data bins: the upper two quantile intervals collapse into one. Reserving the missing slot *before choosing quantiles* gives 255 data bins and 254 cuts. Merely deleting the last existing cut would leave the doubled tail interval in place; the quantile ranks must be regenerated.

This is measured, not just inferred from source. External preprocessing using the current grid reproduces baseline predictions **and tree artifact bytes exactly**. Replacing only the grid with 255 data quantiles gives:

| External binning probe | Feature 0 lowest-bin rows | Highest-bin rows | Test RMSE |
|---|---:|---:|---:|
| Current 256-quantile grid, clamped | 1,562 | 3,125 | 0.163775 |
| 255 data quantiles + reserved missing slot | 1,568 | 1,569 | **0.152451** |

That is a **6.91% RMSE reduction**, enough to explain the original LightGBM-sized deficit in this cell. The corrected-grid probe has identical artifact and prediction hashes at `n_jobs=1` and `10`. Corrected-grid fits took 16.439s and 5.413s respectively **excluding external binning**; do not compare those times to raw-feature fit times.

**Cost/output contract:** small implementation, moderate compatibility testing. Changes new bin boundaries, trees, predictions and fitted metadata. Retain legacy prediction/quantization semantics for already saved cut arrays; do not reinterpret old artifacts using the new data-bin count. Existing cut metadata can represent the new grid, so no new binary tree section is needed. Verify Python/native parity, weighted cuts, sketches, duplicate/constant features, NaNs, minimum bin budgets, U8/U16 boundaries, pickle/save/load, joint and multiclass paths. Current missing-sentinel tests prevent NaN collisions but do not test balanced tail occupancy.

**Falsifiable next step:** implement as a separate modeling change, reproduce this exact result in the native raw-feature path, then run all nine deep configurations and the curated/gate suites across seeds. The production native correction itself has not been implemented or validated here.

### 2. Evaluate binning strategy as an accuracy parameter, before changing model class

**Where:** existing `continuous_binning_strategy` and `continuous_binning_max_bins` in [_core.py](../../bindings/python/alloygbm/_regressor/_core.py), quantile/linear cut construction in [quantization.rs](../../bindings/python/src/quantization.rs), and benchmark factories.

**Mechanism/evidence:** linear 256 improves original RMSE by 18.10%; quantile 1024 improves accuracy but increases observed fit time from roughly 16–17s to 28.24s and widens bin storage. Better border allocation is a stronger immediate direction than globally adding bins. CatBoost uses a different border-selection algorithm, `GreedyLogSum`, rather than Alloy's equal-frequency grid; its [quantization implementation](https://github.com/catboost/catboost/blob/e68a1c021f9c440256e932037abee8f42e62817a/catboost/libs/data/quantization.cpp#L322-L345) exposes that choice.

**Cost/output contract:** no new implementation is required to try the existing linear option. A future per-feature hybrid budget is medium complexity and changes outputs. Do not restore linear as the global default from one Gaussian generator: extreme outliers and concentrated/skewed distributions can make uniform-width bins wasteful. The earlier quantile-default work and its protections still matter.

**Measurement:** compare corrected quantile 256, linear 256, and larger quantile budgets on the existing real-data scenarios plus skew/outlier fixtures. Select using validation splits, reserve test sets for confirmation, and give peers equal tuning time. Save actual borders, tail errors and final tree sizes. A useful target is recovering this fixture's demonstrated improvement without regressing protected real-data strata; no universal percentage improvement is established.

## Ranked CPU implementation experiments

The following speed magnitudes are **hypotheses or conditional bounds, not measured improvements**. The supplied profile puts histogram/scanning at approximately 66%/25% of depth-8 tree building and 36%/62% at depth 12. Total-fit savings are smaller when preparation and other stages matter. Each experiment must pass the absolute-time protocol below independently; their estimated savings are not additive.

### 3. Skip duplicate missing-direction gain evaluation

**Where:** `best_split_for_feature_standard_simd` in [backend lib.rs](../../crates/backend_cpu/src/lib.rs), particularly the unconditional `[true, false]` loop around line 805. Audit scalar/DRO/Morph separately afterward.

**Peer/mechanism:** XGBoost's [numeric split evaluator](https://github.com/dmlc/xgboost/blob/d2aa6ce17dd3270053b20c56440527e020293816/src/tree/hist/evaluate_splits.h#L320-L326) performs the reverse scan only when missing statistics exist. Alloy computes two routing variants even when missing count, gradient and Hessian are all zero. Keep the existing first direction and candidate visitation order; omit only the duplicate work.

**Magnitude:** if directional work were the entire scan, removing half would save at most 12.5% of depth-8 tree time or 31% at depth 12. Prefix/totals/argmax work remains, so expect less; a reasonable pilot target is at least 5% end-to-end on dense depth-12 fits.

**Cost/determinism:** low complexity; intended to preserve current artifact bytes. Test statistics as well as missing count because subtraction can leave zero-count floating residue. Check signed zeros, near ties, default directions and actual NaNs; DRO additionally needs the squared-gradient statistic. Do not reorder scans or copy XGBoost's tie-breaking.

**Falsifier:** unchanged scan count on missing-free data, less than a meaningful absolute-time reduction, or any artifact difference disqualifies the proposed fast path. Compare dense and missing-heavy 500k×40 / 200k×320 at depths 8 and 12.

### 4. Use a constant-Hessian histogram kernel for ordinary squared error

**Where:** `SquaredErrorObjective` in [squared.rs](../../crates/engine/src/objectives/squared.rs), an internal capability hint in [ObjectiveOps](../../crates/engine/src/traits.rs), `BinAccumulator` in [arena.rs](../../crates/backend_cpu/src/arena.rs), and `build_tile_histograms_per_feature` in [backend lib.rs](../../crates/backend_cpu/src/lib.rs).

**Peer/mechanism:** LightGBM's [histogram builder](https://github.com/microsoft/LightGBM/blob/d596b962070090dd4a8e7a1293a379c8b4bd3c36/src/io/dataset.cpp#L1317-L1384) specializes on `USE_HESSIAN`. Alloy updates both Hessian and count for every row even when every Hessian is exactly 1. A safe `{grad: f32, count: u32}` scratch can replace the 16-byte general accumulator, then materialize the existing SoA Hessian column from counts.

**Magnitude:** speculative 3–10% whole-fit improvement in unweighted regression; no expected benefit for general classification. One fewer update and a smaller scratch do not imply a 2× histogram speedup.

**Cost/determinism:** medium. Initially require unweighted squared error, constant leaves, no GOSS/custom/advanced gradient transformations, and total rows at most `2^24`. Under that bound, repeated `+1.0f32` and integer-count conversion agree exactly. Preserve gradient order, subtraction and the final SoA representation; use the general kernel outside this proven subset.

**Falsifier:** compare complete histogram arrays before/after, including subtraction, and artifacts at several thread counts. Benchmark depth 8 first; verify weighted/GOSS/custom cases never enter the specialization. Measure the whole fit including dispatch/materialization, not only a tight loop.

### 5. Avoid child histograms when both children are already terminal

**Where:** `propose_level_node` / `build_tree_level_wise` and `build_tree_leaf_wise` in [tree_build.rs](../../crates/engine/src/trainer/tree_build.rs), child construction around lines 754–824 and 1553–1622.

**Mechanism:** the landed small-node check skips split scanning after an active node already owns its histogram. Child generation still builds the smaller histogram and subtracts for its sibling whenever depth permits. When *both* children have fewer than twice the minimum leaf rows, neither histogram will be useful. Reject that work before allocation/gather/accumulation. Extend to other terminal conditions only with proven bookkeeping equivalence.

**Magnitude:** workload dependent and likely negligible at shallow depth. If fraction `q` of histogram time belongs to such terminal sibling pairs, the upper reduction is `q` times the measured histogram share. For illustration, eliminating 20% of depth-12 histogram work saves about 7.2% of tree-building time; `q` has not been measured.

**Cost/determinism:** medium; preserve stop diagnostics and node IDs. If only the smaller child is terminal, its histogram may still be necessary to derive the larger child by subtraction. Rebuilding the larger child directly changes floating arithmetic and is not a byte-preserving substitute. Do not re-propose the already landed split-scan guard as a new optimization.

**Falsifier:** count histograms built for provably terminal sibling pairs, by depth. Require the same trees, leaves and diagnostics. Reject if the saved work is negligible or scheduling overhead offsets it.

### 6. Reduce SoA histogram materialization and repeated clearing

**Where:** `HistogramArena::resize_for_tile/reset/to_bundle` in [arena.rs](../../crates/backend_cpu/src/arena.rs); per-feature scratch folding and `build_histograms_internal` in [backend lib.rs](../../crates/backend_cpu/src/lib.rs); `HistogramBundle::append` in [histogram.rs](../../crates/core/src/histogram.rs).

**Peer/mechanism:** XGBoost maintains [contiguous reusable histogram storage](https://github.com/dmlc/xgboost/blob/d2aa6ce17dd3270053b20c56440527e020293816/src/tree/hist/hist_cache.h#L19-L45); LightGBM has a [histogram pool](https://github.com/microsoft/LightGBM/blob/d596b962070090dd4a8e7a1293a379c8b4bd3c36/src/treelearner/feature_histogram.hpp#L1369-L1468). Alloy's reusable thread arena still clones its SoA vectors into bundles, collects per-tile results and extends them into one bundle. The per-feature path also zeros the arena, zeros scratch, then adds scratch to the freshly zeroed arena. These are concrete remaining operations despite the earlier allocation-pool work.

Stage experiments separately: preallocate the final bundle and fill disjoint safe slices; recycle freed owned bundles; eliminate redundant destination zeroing only on paths that fully overwrite every active element. Keep SoA. This is not the rejected AoS arena proposal.

**Magnitude:** speculative 2–8% on allocation-sensitive small/deep fits; may be negligible in row-heavy shallow training. Count allocations and copied/zeroed bytes before committing to a larger pool design.

**Cost/determinism:** medium. Maintain arithmetic and feature order, including zero-addition semantics if necessary. Avoid memory-budget-driven eviction/recomputation initially: changing a node from subtraction to direct construction can change model bits. Keep public invariant checks; removing validation is not required to capture the larger allocation/copy opportunity.

**Falsifier:** same artifacts, lower allocation/copied-byte counters, and positive absolute-time movement on both small curated and large dense cases. An arena microbenchmark alone is insufficient.

### 7. Reduce the number of bins/features scored, conservatively

**Where:** global-width `HistogramBundle` in [histogram.rs](../../crates/core/src/histogram.rs), the standard scanner in [backend lib.rs](../../crates/backend_cpu/src/lib.rs), and node feature filtering in [colsample.rs](../../crates/engine/src/colsample.rs).

**Peer/mechanism:** LightGBM uses [per-feature bin offsets](https://github.com/microsoft/LightGBM/blob/d596b962070090dd4a8e7a1293a379c8b4bd3c36/src/io/train_share_states.cpp#L377-L430) and [propagates splittability information](https://github.com/microsoft/LightGBM/blob/d596b962070090dd4a8e7a1293a379c8b4bd3c36/src/treelearner/serial_tree_learner.cpp#L394-L410). Alloy's bundle has one bin width for every feature. Mixed-cardinality columns and deep nodes may pay to score many impossible or duplicate boundaries.

Start with skipping all-invalid gain chunks using existing exact prefix counts and eliminating truly constant features. Later consider variable-width storage or active boundary metadata. Preserve the prefix summation order, original threshold bin, and tie rule. One nonmissing bin **plus missing values can still split**. A feature with weak parent gain may become useful in a child: do not propagate a “low gain” mask as though it proved structural impossibility. Zero-count bins can also contain subtraction residue, so compacting them naively changes sums.

**Magnitude:** near zero on full-cardinality dense roots; potentially material on low-cardinality/deep data. Skipping 25% of a 62%-share split stage gives at most 15.5% less tree time before mask overhead. Measure the actual skipped fraction rather than promising this number.

**Cost/determinism:** medium for gain-chunk rejection, high for variable-width bundles and missing-slot mapping. Train-only storage changes need no artifact-format change; strict output parity is the promotion criterion.

**Falsifier:** instrument candidate thresholds and invalid chunks by depth; compare all-256-bin controls with mixed 4/16/256-bin fixtures, missing data and near ties. Require no dense-control regression and exact models.

## Broader accuracy and benchmark follow-ups

### 8. Improve high-cardinality target encoding as a separate modeling project

**Where:** `fit_transform_target_encoder` in [categorical lib.rs](../../crates/categorical/src/lib.rs), [categorical_bridge.rs](../../bindings/python/src/categorical_bridge.rs), and the mixed-native/target-encoding path in [competitiveness adapters](../../benchmarks/competitiveness/adapters.py).

The non-time-aware encoder fits statistics on all training labels and transforms those same training rows. This creates self-target information and a train/inference mismatch, especially for rare categories; it is not evidence that validation labels leak. CatBoost's [online CTR calculation](https://github.com/catboost/catboost/blob/e68a1c021f9c440256e932037abee8f42e62817a/catboost/private/libs/algo/online_ctr.cpp#L144-L215) reads the prior category statistics before updating them for the current row.

Propose deterministic out-of-fold or ordered training encodings with a full-training inference mapping. Build on Alloy's existing time-aware path where appropriate; chronological data must retain time/group boundaries. The current gate's cardinality-256 column explicitly falls back to target encoding under `max_cat_threshold=255`, so keep that representation visible.

**Magnitude/cost:** no defensible percentage improvement yet; medium/high complexity and additional passes/state. This changes model outputs and needs stable fold/permutation IDs independent of worker count. Use rare-category, unseen-category, random-label and grouped/time controls. Measure held-out log loss and train/test divergence, with native categorical splits and current encoding as baselines. This cannot explain the all-numeric deep-sweep gap.

Several benchmark interpretations also need correction before making stronger claims:

- **CatBoost was running Plain boosting.** `get_all_params()` from all new CatBoost fits records `Plain`, `SymmetricTree`, `GreedyLogSum`, 254 borders, Newton leaf estimation with one iteration, L2=3, random strength=1 and Cosine scoring. Its [default logic](https://github.com/catboost/catboost/blob/e68a1c021f9c440256e932037abee8f42e62817a/catboost/private/libs/options/defaults_helper.h#L33-L42) agrees. The historical report's attribution to ordered boosting is unsupported; ordered categorical statistics are a separate mechanism.
- **Matched maximum depth/rounds is not matched realized capacity.** Record actual leaves/nodes, completed trees, gain thresholds, leaf regularization, sampling scope and effective borders. CatBoost's symmetric trees and LightGBM's leaf-wise growth remain different hypothesis classes. The historical assertion that capacity matching rules out capacity effects is too strong.
- **The curated suite is valuable but not a definitive accuracy authority.** Its displayed five first-place finishes include the four-way wine tie; there are four outright wins in that table. The synthetic categorical row is skipped, not a zero-cost success. Add seeds/splits and equal validation-tuning budgets; report both fixed-resource sensitivity and quality versus elapsed time.
- **XGBoost bit-exactness here is an observation, not its general API promise.** Its [FAQ](https://github.com/dmlc/xgboost/blob/d2aa6ce17dd3270053b20c56440527e020293816/doc/faq.rst#L69-L72) explicitly permits floating-order/multithreading differences. This does not weaken Alloy's guarantee or make determinism a scapegoat for its speed gap.

## Absolute-time A/B protocol for every performance proposal

1. Build baseline and candidate from pinned commits with the same release flags, compiler and Python/dependency versions. Use isolated import paths and record both extension hashes and `alloygbm.__file__`; the runner's current-directory SHA alone cannot prove which installed extension was imported.
2. Use the existing `pr_smoke.yaml`, `published_v1_crosscheck.yaml` and `deep_scaling.yaml` manifests. First run one thread; then matched 4/10-thread budgets. Pin OpenMP/BLAS before imports. Keep data hashes, harness revision, sampling, profiling mode and representation equal.
3. Measure baseline and candidate in the same session, **sequentially**, with alternating ABBA/BAAB blocks and one warmup per arm. Do not run them simultaneously and introduce resource contention. Preserve at least five timed observations per cell, individual seconds, medians and unscaled MAD. The current runner groups repetitions by library, so use a thin outer scheduling layer for build alternation while preserving its raw schema and gate checks.
4. Report `baseline seconds`, `candidate seconds`, `candidate-baseline seconds`, and MAD at each thread count. A better 1→10 ratio does not compensate for slower absolute fits. Apply the existing fail-closed speed/quality gates and disclose missing cells. Do not compare profiled candidates with unprofiled baselines.
5. Run a separate matched `ALLOYGBM_PROFILE=json` diagnosis and add the finding-specific work counters above. Use stage **seconds** to explain the measured change; percentages alone can improve when other stages get slower.
6. For claimed output-preserving changes, compare artifact/prediction bytes across builds and across `n_jobs=1,2,4,10`; compare effective policy, tree sizes and diagnostics too. Run `cargo test --workspace` and `.venv/bin/python -m pytest bindings/python/tests/ -q` before and after implementation, plus focused adversarial cases. Modeling changes instead require explicit allowed-parameter differences and quality gates, while retaining cross-thread equality and old-artifact loading.

An example baseline/candidate invocation, run from each pinned source environment with its own matching extension, is:

```bash
python -m benchmarks.competitiveness.run \
  --manifest benchmarks/competitiveness/manifests/published_v1_crosscheck.yaml \
  --output-dir /tmp/alloy-review-ab-arm \
  --libraries alloygbm --threads 1 --repetitions 5 --warmups 1
```

Use distinct output directories for each build/block. The checked-in old baseline is useful provenance, but is not a substitute for a newly measured control on the same host/session.

## Defer until the above is measured

Do not restart the rejected row-major, branch-hoisting, AoS-arena, thread-pool-cache or row-block-reduction experiments without genuinely new measurements. A complete kernel rewrite is not new evidence by itself. Sparse/EFB and GPU work address different workload classes and do not explain these dense CPU results. F64 or quantized-gradient histograms change models and have bandwidth/accuracy costs; neither is a justified first response to the now-demonstrated binning defect. Existing piecewise-linear leaves and leaf-wise growth remain useful accuracy ablations, but adding another tree family should follow correction of the baseline grid and controlled border/regularization comparisons.

The immediate sequence is **quantile-budget correctness → duplicate missing scans → constant-Hessian and child-histogram experiments → buffer/active-bin work**, keeping modeling and output-preserving performance changes separately reviewable. The checkout is already version 1.0.0, so evaluate changed training outputs as post-1.0 behavior while preserving existing artifact readers.
