## 1. Defects to fix before v1.0

### 1.1 PL leaves diverge when `lambda_l2 = 0` — worse than July **[measured]**

`leaf_model="linear"` with `training_policy="manual"` (which leaves `lambda_l2=0`):
**train RMSE 1,079,067**, test 13.13, predictions spanning (−300, +619). Diagnostics:

| Variant | Train RMSE | Test RMSE | Pred range |
|---|---|---|---|
| PL, manual defaults (λ=0) | 1,079,067 | 13.13 | (−300, 619) |
| PL, `lambda_l2=10` | 0.25 | **0.4456** | (0.3, 5.6) |
| PL, `pl_split_candidates=8` | 0.24 | 1.53 | (−90.5, 19.4) |
| PL, auto policy (sets λ) | 0.25 | 0.4605 | (−1.2, 5.4) |
| PL, 20 rounds (λ=0) | 0.43 | 0.52 | — |

So the solve is healthy when regularized (0.4456 even beats the scalar baseline — the mode
finally pays off), but the λ=0 path passes the PR #106 conditioning guards and then
compounds garbage coefficients round over round. The new shortlist path
(`pl_split_candidates`, PR #136) is *also* affected at its own default interaction — test
RMSE 1.53 with a −90 prediction tail while train looks perfect.

The structural gap (visible at [tree_build.rs clamp sites](../../crates/engine/src/trainer/tree_build.rs)
and [`LinearLeaf::eval`](../../crates/core/src/leaf.rs)): only the **intercept** is clamped
to `max_abs_leaf_value`; the `Σ wⱼ·xⱼ` term is unbounded, so one ill-conditioned solve
produces a leaf whose output on extrapolated rows is arbitrarily large, and nothing
downstream ever detects it.

Fix (small): (a) floor the effective ridge in the PL solve — e.g.
`λ_eff = max(λ, ε · trace(XᵀHX)/d)` — so λ=0 can't produce a near-singular system;
(b) after solving, evaluate the leaf on its own training rows and **fall back to the scalar
leaf if any output exceeds `max_abs_leaf_value`** (keeps predict/SHAP semantics coherent —
a leaf is either valid or scalar, no output clamping needed); (c) add a λ=0 raw-scale
regression test — the current suite pins PL only on well-conditioned configurations, which
is exactly how this regressed unnoticed.

### 1.2 SHAP uses brute-force O(2^N) for every model with ≤ 25 split features **[measured]**

`MAX_EXACT_SPLIT_FEATURES = 25` ([binning.rs:328](../../crates/shap/src/binning.rs:328))
routes any model that splits on ≤ 25 distinct features to the legacy exponential Shapley
path. Measured on a 50-tree depth-6 model: **89 ms/row** at 12 features vs **0.5 ms/row**
at 40 features (TreeSHAP path) — a 180× penalty on the *small* models, and ≤ 25 features
describes a large fraction of real tabular work. TreeSHAP is exact for tree models; the
brute-force path adds nothing for correctness in production.

Fix (one line + tests): route everything through TreeSHAP; keep brute force only as a
`#[cfg(test)]` oracle for parity tests. Separately, the SHAP crate has **no rayon at
all** — rows are embarrassingly parallel, so a `par_iter` over rows is another
cores-× speedup for `shap_values` / `shap_interaction_values` on batches.

### 1.3 Exclusive feature bundling is silently inert under the default binning **[measured]**

On a purpose-built one-hot dataset (40 exclusive columns + 5 dense), `feature_bundling="exact"`
reports `active: False, bundle_count: 0, skipped_feature_count: 45` under the default
`quantile` binning — and the identical fit time confirms nothing was bundled. Switching that
same dataset to `linear` binning: `active: True, bundle_count: 1, bundled_feature_count: 40`.

Mechanism: bundle discovery ([feature_bundling.rs:152](../../crates/core/src/feature_bundling.rs:152))
treats **bin 0 as the "empty" bin** and counts every row in a nonzero bin toward the
25%-occupancy sparsity limit. Quantile binning does not guarantee the dominant zero value
lands in bin 0, so a 97.5%-zero column looks ~100% occupied and every candidate is skipped.
Since quantile is now the default (PR #85 — correctly so), the feature shipped in PR #122
is unreachable for its target use case unless users also change the binning strategy —
and nothing warns them.

Fix (small): identify each feature's **modal bin** during the discovery scan and treat that
as the default/empty bin (offsetting bundled bin encoding accordingly), or map the raw zero
value's bin explicitly. Add the one-hot-under-quantile case to the EFB tests — the current
tests evidently only exercise linear binning.

## 2. Default and configuration changes worth making for v1.0

### 2.1 `n_estimators` defaults to 6

`GBMRegressor().fit(X, y)` trains 6 trees — measured RMSE 1.136 on data with target std
2.1 (barely better than the constant predictor). Every peer library defaults to 100.
Anyone evaluating the package with default construction concludes it doesn't work. Change
to 100 for v1.0 (it's an API-visible change; v1.0 is exactly when to make it).

### 2.2 Ranking: default `lambdarank_truncation_level` and close the remaining gap

Verified the ranking PR series landed (per-group rayon via `par_windows(2)`, per-doc
gain/discount precompute, `ranking_sigma`, truncation). But on finance-shaped data
(50 groups × 2,000 docs, 50 rounds): AlloyGBM 4.26 s all-pairs, 2.37 s with
`truncation_level=50`, vs **LightGBM 0.53 s** — still 4.5–8×. The single biggest lever is
that LightGBM *defaults* truncation to 30 while AlloyGBM defaults to `None` (all pairs —
O(n²) per group). Default `lambdarank_truncation_level=30` for `rank:ndcg` at v1.0, note it
in the changelog, and keep `None` as the opt-out. Secondary: the per-group
`vec![0.0; group_len]` gradient/hessian allocations per round could reuse scratch, and the
pair loop could iterate in sorted-score order for cache locality — profile after the
default change.

### 2.3 DART: add `dart_skip_drop`

DART now completes (calibrated `dart_max_drop=5`, PR #137) but scores 0.624 vs **LightGBM
DART 0.524** at matched drop settings. The likely dominant difference: LightGBM's
`skip_drop=0.5` performs *no dropout at all* on half the rounds, which both speeds training
and improves accuracy on clean data. Adding `dart_skip_drop` (default 0.5, seeded per
round) is small and directly comparable; re-run the PR #137 calibration matrix with it.

### 2.4 Training throughput at scale: 1.5× LightGBM, 2.4× XGBoost

At 250k×50 the accuracy is the best of the three but fit time trails (2.51 s vs 1.63 /
1.03). Not a blocker — but for v1.0 marketing honesty, either close it or say it. The July
architecture items that remain unexploited: interleaved (grad,hess) pair layout in the
histogram kernel, and per-tree in-place row partitioning (the partition path still
allocates per chunk). Profile at this scale before choosing; the CI perf benchmark
(PR #139) should gain a 100k+-row case so scale regressions are visible — the current
gate's dataset is small.

### 2.5 Small polish

- **`training_mode="auto"` is a misleading alias** — it behaves exactly like `"manual"`
  (only `"morph"` changes anything). Either make `"auto"` mean something (e.g. heuristic
  morph activation) or document it as the manual default and deprecate one of the two names
  before the API freezes at v1.0.
- **Mode-level quality pins in CI**: the manual+quantile baseline drifted 0.4568 → 0.4601
  between July and now (deterministic tie-break shifts from the scan refactors — benign,
  but nothing would have caught a real drift). The PR #139 gate checks wall-time; add
  fixed-seed RMSE assertions per mode (standard, subsample, GOSS, DART, PL, morph, DRO) so
  §1.1-class regressions can't land silently again. The PL divergence in this review is
  precisely the case such a pin would have caught.
- **Release mechanics**: `Cargo.toml`/`pyproject.toml` still say 0.12.10 with a populated
  `Unreleased` changelog — routine, but the v1.0 cut should follow
  `docs/reference/release_checklist.md` and decide whether these findings land as 0.12.11
  first or fold into 1.0.0 directly.

  multiclass and joint paths probed clean.
